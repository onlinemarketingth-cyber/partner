## 2. การทดสอบที่ทำจริง

### 2.1 สำรวจโค้ด

อ่านจริงทั้งระบบ: 100 controller · 47 policy · 91 model · `routes/api.php` 1,110 บรรทัด · config ทุกไฟล์ · migration ทุกไฟล์ ·

### 2.2 เขียนเทสต์โจมตีแล้วรันจริง — นี่คือส่วนที่ต่างจากการเดา

ก่อนแก้โค้ด ผมเขียนเทสต์ที่ **assert พฤติกรรมที่พัง** แล้วรันให้เขียว เพื่อพิสูจน์ว่าช่องโหว่มีจริง

```
PASS SecurityAuditProofTest   ← ผลตอนยังไม่แก้
 ✓ ตัวแทนยืนยันเงินออเดอร์ตัวเองโดยไม่มีสลิป แล้วได้คอมมิชชั่น
 ✓ แอดมินบริษัท A อ่านข่าวสารที่ยังไม่เผยแพร่ของบริษัท B ได้
 ✓ ตัวแทนบริษัท A อ่าน Badge / ของรางวัลของบริษัท B ได้
```

หลังแก้แล้ว **พลิก assertion เป็นฝั่งปลอดภัย** ไฟล์เดียวกันจึงกลายเป็นเทสต์กันการถอยกลับ
และเทสต์ audit log ผมพิสูจน์ด้วยการ**ถอดโค้ดออกแล้วรันซ้ำ**ให้เห็นว่ามันแดงจริง ก่อนใส่กลับ

### 2.3 สแกน dependency

`npm audit` ทั้งสองแอป เจอของจริง — **pdfjs-dist 6.1.200 รันโค้ดได้จาก PDF ที่ถูกดัดแปลง**
ระบบนี้ให้ตัวแทนอัปโหลด PDF แล้วแอดมินเปิดดูใน viewer ในแอป = ครบวงจรพอดี

`composer audit` **รันไม่ได้** — sandbox นี้ถูกบล็อกไม่ให้ต่อ packagist (403) ตรวจเวอร์ชันด้วยมือแทน:
Laravel 12.66 · Symfony 7.4 · Sanctum 4.3.3 ไม่มีตัวไหนค้างเมเจอร์เก่า **แต่นั่นไม่ใช่การเช็ค CVE จริง**

## 4. งานค้าง

### 4.1 🔴 ต้องคนทำ — โค้ดพร้อมแล้ว รอปฏิบัติการ

**(ก) แยก session ฝั่งแอดมิน (V6)** — ลำดับนี้ห้ามสลับ

1. สร้าง `api-admin.partner.syncvision.io` ชี้ไป document root เดียวกับ API เดิม (`backend/public`)
2. เพิ่ม `https://admin.partner.syncvision.io` ใน `ADMIN_FRONTEND_URL` และ `SANCTUM_STATEFUL_DOMAINS`
3. ~~ยืนยัน `SESSION_DOMAIN` ไม่ได้ตั้งค่า~~ — **คำแนะนำนี้ผิด แก้แล้ว 2026-08-21 ดู §4.1(ก-แก้ไข) ด้านล่าง**
4. แก้ `frontend-admin/.env.production` → `VITE_API_BASE_URL=https://api-admin.partner.syncvision.io`
5. deploy แล้ว**ล็อกอินสองแอปพร้อมกันในเบราว์เซอร์เดียว** = acceptance test ของงานนี้

> **ทำข้อ 4 ก่อนข้อ 1 = แอดมินล็อกอินไม่ได้ทันทีที่ deploy**
> ผมแก้แค่ `.env.production.example` **ไม่ได้แตะไฟล์จริงของคุณ** โดยตั้งใจ
> (และเครื่องมือปฏิเสธการเขียน `.env.production.example` ลงเครื่องคุณด้วย — ต้องคัดลอกจากไฟล์ที่ผมส่งให้เอง)

#### 4.1(ก-แก้ไข) 🔴 ผมแนะนำผิด — อ่านตรงนี้ก่อนทำอะไรกับ `SESSION_DOMAIN`

**ตรวจ `.env` production จริงเมื่อ 2026-08-21 พบว่า `SESSION_DOMAIN=.partner.syncvision.io` ตั้งอยู่ — และมัน "จำเป็นต้องมี"**

ผมเคยเขียนว่าต้องไม่ตั้งค่า **ซึ่งผิด และถ้าทำตามจะทำให้ production พังทันที**

เหตุผลที่มันจำเป็น: `client.ts` ของทั้งสองแอปอ่าน `XSRF-TOKEN` จาก `document.cookie` แล้วส่งกลับเป็น header
บน production หน้าเว็บอยู่ที่ `partner.syncvision.io` แต่ API อยู่ที่ `api.partner.syncvision.io` — **คนละโฮสต์**
ถ้า cookie เป็น host-only มันจะผูกกับโฮสต์ของ API และ JS บนหน้าเว็บ**อ่านไม่เห็น** → ทุก POST/PUT/DELETE ล้มด้วย CSRF mismatch

ที่ local ไม่เจอปัญหานี้เพราะ `agent.localhost:5178` กับ `agent.localhost:8010` เป็น**โฮสต์เดียวกัน** ต่างแค่พอร์ต ซึ่ง cookie ไม่สนใจ
นี่คือเหตุผลว่าทำไมสภาพแวดล้อม local ถึงไม่สะท้อนความจริงข้อนี้ และทำไมผมถึงพลาด

**ผลต่อแผน D5:** การเพิ่ม subdomain `api-admin` **เพียงอย่างเดียวแก้ V6 ไม่ได้** เพราะ `SESSION_DOMAIN=.partner.syncvision.io`
ครอบทุก subdomain รวมทั้ง `api-admin.partner.syncvision.io` ด้วย cookie จึงยังใช้ร่วมกันอยู่ดี

**ทางเลือกจริงมี 3 ทาง ต้องให้ human ตัดสิน — ยังไม่ได้ทำอะไรทั้งสิ้น**

| ทาง | ทำอะไร | แลกอะไร |
|---|---|---|
| **A. API อยู่โฮสต์เดียวกับหน้าเว็บ** | เสิร์ฟ API ที่ `partner.syncvision.io/api/*` และ `admin.partner.syncvision.io/api/*` แล้ว**ถอด `SESSION_DOMAIN` ออกได้จริง** | แยกขาดสมบูรณ์ ถูกต้องตามตำรา · แต่ต้องรื้อ document root / symlink บน Hostinger และแก้ `VITE_API_BASE_URL` ทั้งสองแอป — งานใหญ่และเสี่ยงที่สุด |
| **B. แยกชื่อ cookie ต่อแอป** | ตั้งชื่อ session cookie ต่างกันตาม Origin + override `ValidateCsrfToken` ให้ชื่อ XSRF ต่างกันด้วย | ไม่ต้องแตะ DNS/โครงสร้าง · แต่**แยกได้ไม่ขาด**: cookie ยังอยู่บน `.partner.syncvision.io` ทั้งคู่ JS บน origin หนึ่งยังอ่าน XSRF ของอีก origin ได้ (session cookie เป็น HttpOnly อ่านไม่ได้ แต่ token อ่านได้) |
| **C. ยอมรับแล้วลดความเสี่ยงแทน** | ไม่แตะโครงสร้าง แต่เปิด CSP เต็มบน agent portal และถือว่า XSS บน origin นั้นคือภัยตัวจริงที่ต้องกัน | ถูกและเร็วที่สุด · แต่ไม่ได้แก้ V6 จริง แค่ทำให้ใช้ประโยชน์จากมันยากขึ้น |

ผมเอนไปทาง **A** ถ้ารับความเสี่ยงงานโครงสร้างได้ และ **C ทำควบคู่ไปก่อนได้ทันที** ไม่ว่าจะเลือกอะไร

### 4.2 🟡 ต้องยืนยันในเบราว์เซอร์จริงก่อนเปิดใช้

**(จ) CSP ฉบับเต็ม** — `frame-ancestors` (กัน clickjacking ซึ่งคือช่องโหว่ที่เจอจริง) **เปิดแล้ว**
แต่ CSP ที่คุม `script-src`/`connect-src` ยัง comment ไว้ใน `.htaccess` ทั้งสองไฟล์ พร้อมบรรทัดที่เขียนไว้ให้

เหตุผล: **CSP ที่ผิดไม่เตือน มันทำให้หน้าจอขาว** ทางเดียวที่จะจูนอย่างซื่อสัตย์คือเปิดทุกหน้าในเบราว์เซอร์แล้วอ่าน console
ผมทำแบบนั้นจากที่นี่ไม่ได้ การเปิดไปเลยคือแลกความเสี่ยง clickjacking กับความเสี่ยงเว็บล่ม

**(ฉ) `sandbox` บน iframe** — ช่องโหว่จริงปิดด้วยการกรอง protocol แล้ว `sandbox` เป็นเกราะชั้นสอง
แต่ตั้งผิด**ทำให้คลิปหยุดเล่นแบบเงียบ ๆ ทั้งระบบ** จึงไม่ใส่มั่ว ๆ

**(ช) `.htaccess` ที่แก้ไปต้องทดสอบหลัง deploy** — ไฟล์นี้เคยทำ production ล่มมาแล้ว (TASK-231)

```bash
curl -sI https://partner.syncvision.io/login | grep -i 'x-frame\|x-content\|referrer'
```

และต้องเปิด deep link สักอันให้แน่ใจว่าไม่ 404

### 4.3 🟡 ฟีเจอร์ที่ยังไม่ครบ

**(ซ) ปุ่มคืนเงินยังไม่มีในหน้าจอ** — API พร้อมและมีเทสต์ 10 ตัว แต่ยังต้องเรียก `POST /orders/{id}/refund` พร้อม `reason` เอง
เป็นงานฝั่งหน้าจอล้วน ๆ แยกออกมาทำได้

**(ฌ) เคสจ่ายเงินสด/ส่งสลิปทาง LINE ตันอยู่** — ทางเดียวที่ได้สถานะ `AwaitingVerification` คือลูกค้าอัปโหลดสลิปเองที่หน้า `/pay`
**ยังไม่ได้ทำฟีเจอร์ให้แอดมินอัปโหลดแทน** เพราะยังไม่มีคำตอบว่าใครควรทำได้ — ผมเขียนคำเตือนไว้ในโค้ดตรงจุดนั้นแล้ว
**นี่คือข้อที่กระทบการใช้งานจริงมากที่สุดในรายการนี้**

### 4.4 ⚪ ค้างจากงานก่อนหน้า (ไม่ใช่เรื่องความปลอดภัย)

- ลิงก์ 4 กลุ่มที่ยังไม่ได้คลิกทดสอบ: `/j/` `/pay/` `/l/` `/m/`
- **ตัวเลข conversion ยังไม่เคยเห็นขยับจาก 0** ยืนยันด้วยเทสต์อัตโนมัติเท่านั้น
- QR ยังไม่ได้ต่อเข้ากับ 3 หน้าลิงก์ใหม่
- PDPA: เก็บ referrer host + user agent + ip hash ควรมีข้อความในนโยบายความเป็นส่วนตัว (ผมไม่ใช่นักกฎหมาย)
- `tracked_link_visits` ยังไม่มีแผน archive
- `used_count` ของลิงก์สมัครบริษัทไม่มี row lock

## 5. ข้อจำกัดที่ต้องรู้ — สิ่งที่ผมพิสูจน์ไม่ได้

1. **V2 (คอมมิชชั่นซ้ำ) ยืนยันจากการอ่านโค้ด ไม่ได้พิสูจน์ด้วยเทสต์** — SQLite แปล `lockForUpdate()` เป็นค่าว่าง
   **เทสต์เขียวไม่ได้แปลว่า lock ทำงาน** มันพิสูจน์ตัวเองบน MySQL production เท่านั้น เขียนไว้ในคอมเมนต์แล้ว
2. **ค่า `.env` จริงบน production** — ผมเข้าเซิร์ฟเวอร์ไม่ได้
3. **`composer audit`** — sandbox ถูกบล็อก
4. **`.env` เข้าถึงผ่านเว็บได้ไหม** — ขึ้นกับ document root ทดสอบด้วยการเปิด `https://api.partner.syncvision.io/.env` (ควรได้ 403/404)
5. **การ stage ไฟล์จากเครื่องคุณถูกปฏิเสธ** (`untrusted_device` — เซสชันแอปเดสก์ท็อปหมดอายุ)
   การเขียนไฟล์ลงเครื่องยังทำได้ แต่ถ้าจะให้ผม**อ่าน**ไฟล์จากเครื่องคุณอีก ต้องล็อกอินแอป Claude ใหม่ก่อน

## 6. ความผิดพลาดของผมในงานนี้

**รัน `pint app/` ทั้งโฟลเดอร์แทนที่จะรันเฉพาะไฟล์ที่แก้** — เป็นบทเรียนที่ผมเคยเจอมาแล้วรอบก่อนและเขียนไว้เองว่าห้ามทำ
pint จัดรูปแบบไฟล์ที่ผมไม่ได้แตะไป 39 ไฟล์ในสำเนาคลาวด์ของผม

**ไม่มีไฟล์ไหนหลุดไปถึงเครื่องคุณ** — ผมส่งเฉพาะรายชื่อที่ตั้งใจแก้และตรวจก่อนส่งทุกครั้ง
บันทึกไว้เพื่อให้ตรวจย้อนหลังได้ ถ้า diff ของคุณมีไฟล์แปลกปลอมโผล่มา ให้สงสัยข้อนี้ก่อน

## 7. สถานะ repo และขั้นตอนถัดไป

commit ล่าสุดบนเครื่องคุณคือ `b104e0b feat(links): one short-link system...` — งานลิงก์ commit แล้ว
งานความปลอดภัยทั้งหมด (**51 ไฟล์เปลี่ยน ใหม่ 10**) **ยังไม่ commit**

**ลำดับที่แนะนำ:**

1. `php artisan test` บนเครื่องคุณให้เห็น 1,724 ผ่านด้วยตาตัวเอง
2. `php artisan migrate` (มี migration ใหม่ 1 ตัว — เปลี่ยน `amount_satang` เป็น signed + คอลัมน์ refund)
3. commit แยกเป็นก้อนความปลอดภัย
4. **ตรวจ `.env` production ตาม §4.1(ข) ก่อน deploy** — โดยเฉพาะ `FRONTEND_URL` / `ADMIN_FRONTEND_URL` ที่จำเป็นแล้ว
5. deploy → ตรวจ header ตาม §4.2(ช) → เปิด deep link ให้แน่ใจว่าไม่ 404
6. ค่อยทำ subdomain แยก session (§4.1(ก)) เป็นงานถัดไปแยกรอบ

> **อย่ารวมขั้น 5 กับ 6 ในรอบเดียว** ถ้าอะไรพัง จะแยกไม่ออกว่าเป็นเพราะ header หรือเพราะ session
