### TASK-237 — `php artisan user:super-admin`

**ปัญหา (G1):** API ปฏิเสธการสร้าง Super Admin ทุกระดับโดยตั้งใจ ทางเดียวที่เหลือคือ seeder หรือ tinker — และ tinker เปิดไม่ได้บน Hostinger (`Call to undefined function shell_exec()`) ถ้าวันนี้บัญชี Super Admin เดียวที่มีถูกล็อกออก **ไม่มีทางกู้บน production เลย**

**ต้องทำ**

- command ใหม่ รับ `--email` `--name` และถามรหัสผ่านแบบ **`secret()` (ไม่ echo ไม่ลง history)**
- ถ้าอีเมลมีอยู่แล้ว → เลื่อนเป็น Super Admin แทนการสร้างซ้ำ และ**ถามยืนยันก่อน**
- ตั้ง `email_verified_at` ให้เลย (ไม่งั้นติดด่าน LoginGateService ทันที)
- **เขียน audit `user.super_admin_granted`** พร้อม actor = `null` และ new_values บอกว่ามาจาก CLI — การได้สิทธิ์สูงสุดต้องมีร่องรอยเสมอ แม้จะมาจากบรรทัดคำสั่ง
- ปฏิเสธเมื่อ `APP_ENV=production` **เว้นแต่** ใส่ `--force` — กันมือลั่นบนเครื่องจริง

**เกณฑ์ผ่าน (เขียนเป็นเทสต์)**

1. รันแล้วได้ Super Admin ที่ล็อกอินผ่านทั้ง 5 ด่านของ LoginGateService
2. อีเมลซ้ำ → เลื่อนขั้น ไม่สร้างแถวใหม่ และ role เดิมถูกบันทึกใน `old_values`
3. มี audit row เสมอ
4. รหัสผ่านไม่ปรากฏใน output, ไม่อยู่ใน argument, ไม่อยู่ใน audit
5. บน production ที่ไม่มี `--force` → ไม่ทำอะไรเลย

**ห้าม:** เพิ่ม endpoint HTTP สร้าง Super Admin — ข้อห้ามนี้คือของเดิมและยังอยู่

### TASK-238 — สิทธิ์เปลี่ยน = token ตาย

**ปัญหา (G2):** `UserService` ปิดบัญชี/เปลี่ยน role/รีเซ็ตรหัสผ่านได้ แต่ **ไม่แตะ `personal_access_tokens`** คนที่เพิ่งถูกปิดบัญชีจึงถือ token ที่ยังใช้ได้อีกไม่เกิน 12 ชม. บนระบบที่โอนเงินได้

**ต้องทำ** — ถอน token ทั้งหมดของผู้ใช้นั้นเมื่อเกิดเหตุใดเหตุหนึ่ง

1. ปิดบัญชี (`user.deactivated`)
2. เปลี่ยน role (`user.role_changed`)
3. แอดมินรีเซ็ตรหัสผ่าน (`user.password_reset_by_admin`)
4. ผู้ใช้เปลี่ยนรหัสผ่านเอง (`user.password_changed`) — **ยกเว้น token ของ session ปัจจุบัน** ไม่งั้นเปลี่ยนรหัสผ่านแล้วเด้งตัวเองออกทันที
5. ย้ายบริษัท (`moveToCompany`) — ข้ามบริษัทคือข้ามขอบเขต BR-6

**เกณฑ์ผ่าน**

1. เทสต์ต่อเหตุการณ์: ถือ token ไว้ → เกิดเหตุ → เรียก API ด้วย token เดิม → **401**
2. กรณีที่ 4 เท่านั้นที่ token ปัจจุบันยังใช้ได้ต่อ
3. ผู้ใช้ที่ล็อกอินด้วย cookie (admin console) ไม่ได้รับผลกระทบ — `TransientToken` ไม่ใช่ `PersonalAccessToken`

### TASK-239 — ตรวจของจริง (ag-qa)

รัน TASK-237 บน production จริง (สร้างบัญชีทดสอบแล้วปิดทิ้ง) · ยืนยันว่า TASK-238 ทำให้ token ตายจริงด้วย token ที่ขอมาเอง · ยืนยันว่า audit row เกิดครบ

### TASK-240 — backend

**ต้องทำ**

- `AuditLogController::index` รับ `?actor_user_id=` เพิ่ม (ของเดิมมี `action`, `date_from`, `date_to`, `company_id`)
  **BR-6:** Company Admin ต้องกรองได้เฉพาะคนในบริษัทตัวเอง — ส่ง id ของคนบริษัทอื่นต้องได้ผลว่าง ไม่ใช่ 403 ที่บอกใบ้ว่ามีคนนั้นอยู่จริง
- migration เพิ่ม index (G4): `(actor_user_id, created_at)` และ `(company_id, created_at)`
  เหตุผลที่เป็น composite ไม่ใช่คอลัมน์เดี่ยว: ทุกคำถามจริงคือ "คนนี้/บริษัทนี้ ในช่วงเวลานี้" และหน้าจอเรียงตามเวลาเสมอ
- บันทึกล็อกอินล้มเหลว (G5) — action `auth.login_failed`
  - `actor_user_id` = id ถ้าอีเมลมีในระบบ, `null` ถ้าไม่มี
  - **ห้ามบันทึกรหัสผ่านที่กรอก และห้ามบันทึกอีเมลที่ไม่มีในระบบลง `new_values`** (เท่ากับสร้างลิสต์อีเมลให้คนอ่าน log) — เก็บแค่ IP กับเหตุผล
  - บันทึกเหตุผลจาก `LoginBlockReason` ด้วย: บัญชีถูกปิด/รออนุมัติ/บริษัทถูกปิด ต่างจาก "รหัสผ่านผิด" คนละเรื่องกันสิ้นเชิงเวลาสืบ
  - **ระวัง flooding:** บอทยิงรหัสผ่านทำให้เกิดหลายพันแถวได้ ให้เขียนเฉพาะเมื่อ rate limiter ยังไม่ล็อก + บันทึก `auth.lockout` หนึ่งแถวตอนถูกล็อก

**เกณฑ์ผ่าน**

1. Super Admin กรองตาม actor ได้ทุกบริษัท
2. Company Admin กรองคนบริษัทอื่น → ผลว่าง
3. `EXPLAIN` ยืนยันว่า query ใช้ index ใหม่
4. รหัสผ่านผิด → มี `auth.login_failed` 1 แถว ไม่มีรหัสผ่านอยู่ในนั้น
5. อีเมลไม่มีในระบบ → มีแถว แต่ไม่มีอีเมลใน payload
6. ถูก rate limit → มี `auth.lockout` 1 แถว ไม่ใช่แถวละครั้งที่ยิง

3. Company Admin เห็นเฉพาะคนในบริษัทตัวเองใน combobox
4. เทสต์: ตัวกรองถูกส่งไปที่ API จริง (ไม่ใช่กรองในเบราว์เซอร์ — หน้านี้แบ่งหน้า การกรองฝั่ง client จะโกหก)

## 4. Sprint 4 — ต้องได้คำตอบก่อนจึงเริ่มได้ (BR-7)

**ห้ามเริ่ม task ในสปรินต์นี้จนกว่า human จะตอบ** ค่าที่ยังไม่ตัดสินคือค่าจริง ไม่ใช่ค่าที่ ag-lead คิดเองได้

| คำถามที่ค้าง | บล็อก task |
|---|---|
| **ก.** บันทึกการ "เปิดดู" ข้อมูลด้วยไหม (PDPA) — ถ้าเอา log จะโตหลายสิบเท่า | TASK-247 |
| **ข.** ใครดู audit ได้ — คง Company Admin ไว้ หรือจำกัดเฉพาะ Super Admin | TASK-247 |
| **ค.** เก็บ log นานแค่ไหน (1 ปี / 2 ปี / ตลอดไป) | TASK-248 |
| **ง.** เอา 2FA ไหม และบังคับกับใคร (ทุกคน / เฉพาะแอดมิน / สมัครใจ) | TASK-249 |
| **จ.** ต้องการสิทธิ์รายคน (เช่น "แอดมินที่ดูได้แต่แก้ไม่ได้") ไหม | TASK-250 |

- **TASK-247** บันทึกการเปิดดูข้อมูลอ่อนไหว — ต้อง**เขียน ADR-040 ก่อน** เพราะเปลี่ยนความหมายของตาราง audit จาก "การเปลี่ยนแปลง" เป็น "การใช้งาน" และต้องมาคู่กับ TASK-248 เสมอ
- **TASK-248** นโยบายลบ log เก่า — command + scheduled task · ต้องกันการลบแถวที่กฎหมายอาจต้องการ (เงิน/สิทธิ์) โดยแยกอายุตามประเภท
- **TASK-249** 2FA — ต้องมี ADR ของตัวเอง (กู้บัญชีเมื่อทำอุปกรณ์หาย คือส่วนที่ยากกว่าตัว 2FA เอง)
- **TASK-250** สิทธิ์รายคน — คือ Phase 2 ของ ADR-032 ซึ่ง**มีที่ว่างเตรียมไว้แล้ว**ใน `PermissionResolver::may()` อย่าออกแบบใหม่ ให้ต่อจากที่มี

## 5. ลำดับการทำงานที่แนะนำ

```
Sprint 1  ─ ag-dev ทำ 237 + 238 ขนานกันได้ ─ ag-qa ตรวจ 239
Sprint 2  ─ ag-dev ทำ 240 ให้เสร็จก่อน ─ ag-ui ทำ 241 ขนานกับ 242 ─ ag-qa ตรวจ 243
```

## 6. กฎที่ใช้กับทุก task ในเอกสารนี้

1. **เทสต์ต้องพิสูจน์ว่าจับบั๊กได้จริง** — ใส่บั๊กกลับเข้าไปแล้วเทสต์ต้องแดง ถ้าไม่แดง เทสต์นั้นไม่ได้ทดสอบอะไร (บทเรียนจาก 2026-09-04: เทสต์ media 10 ตัวผ่านทั้งที่ระบบส่ง header ผิด เพราะไม่มีตัวไหนอ่าน header)
2. **BR-6 ทุกจุดที่รับ id จาก client** — Company Admin ต้องกรองข้ามบริษัทไม่ได้ และผลลัพธ์ต้องเป็น "ว่าง" ไม่ใช่ error ที่บอกใบ้ว่ามีข้อมูลอยู่
3. **ห้ามใส่ `Gate::before` ให้ Super Admin** ไม่ว่าจะสะดวกแค่ไหน
4. **ห้ามให้ log เก็บความลับ** — รหัสผ่าน, token, เลขบัตร, เลขบัญชี ต้องไม่ปรากฏใน `old_values`/`new_values` แม้แต่ในกรณี error
5. **คอมเมนต์เขียนว่า "ทำไม" ไม่ใช่ "อะไร"** — และถ้าแก้พฤติกรรมเดิม ให้เขียนไว้ว่าของเดิมคืออะไรและทำไมถึงเปลี่ยน
6. **แก้เอกสารพร้อมโค้ด** — ถ้า task ไหนทำให้ประโยคใน ADR-032 หรือหน้าจอไม่จริงอีกต่อไป ให้แก้ในคอมมิตเดียวกัน
