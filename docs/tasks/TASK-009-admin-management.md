Input: `Company`/`User` models (pre-existing, unmodified structurally — `Company` has `SoftDeletes` + no `TenantScope` by design; `User` has `SoftDeletes` + `TenantScope`), `CompanyPolicy` (pre-existing, unused until now), Phase 6's full `gamification_rules`/`badges`/`user_badges` API (unmodified, this phase only builds the frontend for it).

**3 decisions confirmed by the human before backend design started** (via AskUserQuestion — not guessed):
  1. No email/invite system exists anywhere in this codebase. New-agent password: the Admin types a temporary password directly into the create form and communicates it out of band (not auto-generated, not emailed).
  2. Company Admin CAN change an existing team member's role between `agent` and `company_admin` (promote/demote), but only within their own company — never touching `super_admin` in either direction.
  3. "Deleting" an agent is a soft-delete/deactivate (the `User` model already had `SoftDeletes` — this just uses it for the first time), reversible via a restore action, not a permanent destructive delete.

Expected output:
- **Manage Companies** (Super Admin only, end to end): `StoreCompanyRequest`/`UpdateCompanyRequest`, `CompanyService` (`create`/`update`/`delete`, all three now — `delete()` was added after structural review flagged the Controller bypassing the Service layer, see Verification status), `CompanyResource` (includes `user_count` via `withCount`/`loadCount`), `CompanyController` (full CRUD via the pre-existing `CompanyPolicy`). No cascading logic on deactivate/delete — flagged as an open gap (see Design notes), not invented.

Acceptance Criteria:
  - Super Admin can create/list/update/soft-delete a Company; Company Admin/Agent cannot create/list one, but Company Admin can view their own single company (verified: `CompanyTest`, 8 tests)
  - A Company Admin can create a new agent (or company_admin) in their own company with a temporary password they typed themselves; the same request with an explicit `company_id` is rejected at validation, never silently corrected (verified: `test_company_admin_can_create_a_new_agent_with_a_temporary_password`, `test_company_admin_cannot_set_company_id_when_creating_a_user`)
  - Creating OR updating a user to `role: super_admin` is rejected (422) at every actor level, on both the create and update paths (verified: `test_company_admin_cannot_create_a_super_admin`, `test_company_admin_cannot_promote_an_agent_to_super_admin` — the latter added specifically to close a test-coverage gap found in structural review, see below)
  - A Company Admin can promote an existing agent to `company_admin` (human-confirmed scope) within their own company (verified: `test_company_admin_can_promote_an_agent_to_company_admin`)
  - No `super_admin` row is ever visible or editable through `/users`, even to another Super Admin, and never appears in the index list (verified: `test_super_admin_row_is_never_visible_through_this_endpoint`, `test_super_admin_row_is_excluded_from_the_index_list`)
  - Cross-company access to a `/users/{id}` row is 404 (User IS TenantScope'd — binding fails before the Policy runs); cross-company access to a `/companies/{id}` row is 403 (Company is NOT TenantScope'd by design — the Policy is the only gate). Both are the correct, verified mechanism for each model, not an arbitrary inconsistency (verified: `test_cross_company_user_access_is_404`, `test_company_admin_cannot_view_another_companys_details`)
  - A Company Admin can never deactivate their own account (self-lockout guard), and can never deactivate/view/edit a colleague in another company (verified: `test_company_admin_cannot_deactivate_themselves`, cross-company tests above)
  - A deactivated agent's history (referrals/commission/XP) is untouched (soft-delete only) and the account can be restored (verified: `test_company_admin_can_deactivate_an_agent`, `test_a_deactivated_agent_can_be_restored`)
  - A Company Admin can reset a locked-out agent's password; an Agent can never reset a colleague's password (verified: `test_company_admin_can_reset_an_agents_password`, `test_agent_cannot_reset_a_colleagues_password`)
  - No password is ever hashed manually or echoed back in any API response — entirely via `User`'s existing cast + `$hidden`

Out of scope (future tasks):

Design notes (not in CLAUDE.md, decided here — flag if wrong):
  - `UserResource` is shared between the pre-existing `/me`/`/login` responses and this phase's new "Manage Agents" screen, rather than creating a second, near-duplicate Resource — the added fields (`has_passed_basic_cert`, `is_active`, `created_at`, `deleted_at`) are additive and harmless for the auth-response case, judged simpler than maintaining two Resources with 90% overlap. Revisit if the auth response ever needs to actively exclude these fields for a reason not yet apparent.
  - The Gamification Config screen's "ตั้งเป็นค่า default ของทั้งแพลตฟอร์ม" checkbox (Super Admin only) is the one UI surface that can create a `gamification_rules` row with `company_id = null` — everything else in this phase (agents, companies) has no equivalent "platform-wide" concept, since neither `User` nor `Company` themselves have a nullable-company-id design.
