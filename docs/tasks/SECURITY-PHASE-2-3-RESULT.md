## 2. การตัดสินใจที่อยากให้ตรวจ

### 2.1 คืนเงิน = เขียนแถวติดลบ ไม่ใช่ธง

`amount_satang` เดิมเป็น `unsignedBigInteger` เก็บค่าติดลบไม่ได้ ผมเปลี่ยนเป็น **signed**

เหตุผล: ยอดเงินทุกที่ในระบบคือ `SUM(amount_satang)` — สรุปค่าคอม, CSV จ่ายเงิน, ยอดขายรวม, leaderboard
แถวติดลบทำให้**ทุกยอดถูกต้องทันทีโดยไม่ต้องแก้ query สักบรรทัด** ส่วนทางเลือกอีกทาง (เก็บค่าบวก + ธง `is_reversal`)
จะทำให้ยอดทุกตัว**ผิดเงียบ ๆ** จนกว่าจะไล่แก้ครบ และมันพังแบบเปิด — query ที่ลืมแก้จะยังจ่ายค่าคอมที่คืนไปแล้วและดูถูกต้องด้วย

`down()` ของ migration **ปฏิเสธการ rollback** ถ้ามีแถวติดลบอยู่ เพราะ MySQL ไม่ error แต่**ปัดเป็น 0** — ค่าคอมที่คืนไปแล้วจะกลับมาเป็นหนี้อีก

### 2.2 คืนเงินกลับค่าคอมมิชชั่น **ทุกแถว** ของ referral นั้น ไม่ใช่แค่ของตัวแทนคนขาย

ขายครั้งเดียวอาจจ่าย 5 คน — คนขาย, upline override, co-agent split, matrix/generation override, binary credit
ถ้ากลับเฉพาะแถวตรง แถว override จะค้างอยู่บนการขายที่ไม่มีแล้ว และ**นั่นคือแถวที่ไม่มีใครนึกถึงว่าต้องเช็ค**

### 2.3 คืนเงินไม่ถอย pipeline stage กลับ

`PipelineService` เดินหน้าอย่างเดียว และการคืนเงินไม่ใช่ที่ที่ควรไปประดิษฐ์การเดินถอยหลัง
การขายไปถึง Complete Payment จริง นั่นคือประวัติศาสตร์และยังจริงอยู่ สิ่งที่เปลี่ยนคือ**เงิน** ซึ่งอยู่ในบัญชีค่าคอมกับบนออเดอร์ และทั้งคู่บอกแล้ว

### 2.4 ค่าคอมที่จ่ายไปแล้ว → แถวกลับรายการถูกทำเครื่องหมาย "จ่ายแล้ว" ด้วย

เพื่อให้ยอด "ค้างจ่าย" ยังจริง การคืนเงินต้องไม่กลายเป็นหนี้ค้างฝั่งตัวแทน และต้องไม่ไปหักรอบจ่ายที่ออกไปแล้วเงียบ ๆ
**การเรียกเงินคืนจากตัวแทนที่รับไปแล้วเป็นเรื่องที่คนต้องคุยกัน ไม่ใช่แถวที่ service นี้จะประดิษฐ์เอง**

### 2.5 `uncompromised()` ปิดในเทสต์เท่านั้น ไม่ปิดใน local

fixture ของเทสต์ใช้รหัส `"password"` ตรง ๆ (ซึ่ง uncompromised ควรปฏิเสธ) และเทสต์ต้องไม่ยิงเน็ตทุก assertion
แต่ **local ใช้กฎเดียวกับ production** — dev ที่ตั้งรหัสอ่อนบนเครื่องตัวเองไม่ได้ จะได้ไม่แปลกใจตอนขึ้น production
ถ้า HaveIBeenPwned ล่ม Laravel **fail open** ไม่บล็อกการสมัคร

### 2.6 ไม่เก็บอีเมลของ lockout ที่ไม่ตรงกับบัญชีใคร

ถ้าอีเมลไม่มีในระบบ บันทึกแค่ `target_exists: false` กับ IP — การเก็บอีเมลคนแปลกหน้าไว้ไม่มีกำหนดคือข้อมูลส่วนบุคคลที่ระบบนี้ไม่มีเหตุผลต้องถือ (PDPA)

## 3. ⚠️ ที่ยังไม่จบ และเป็นงานของคนไม่ใช่ของโค้ด

### 3.1 V6 — ต้องสร้าง subdomain ก่อน แล้วค่อยสลับไฟล์

ผมแก้ **`.env.production.example`** ให้แล้ว แต่**ไม่ได้แตะ `.env.production` ตัวจริงของคุณ** โดยตั้งใจ

ลำดับที่ห้ามสลับ:

1. สร้าง `api-admin.partner.syncvision.io` บน Hostinger ชี้ไป **document root เดียวกับ API เดิม** (`backend/public`)
2. เพิ่ม `https://admin.partner.syncvision.io` ใน `ADMIN_FRONTEND_URL` และ `SANCTUM_STATEFUL_DOMAINS` (สองตัวนี้คือ origin ของ**หน้าเว็บ** ไม่ใช่ของ API)
3. ยืนยันว่า `SESSION_DOMAIN` **ไม่ได้ตั้งค่า** — ถ้าตั้งเป็นโดเมนแม่ cookie จะกลับมารวมกันและงานนี้เป็นโมฆะ
4. แก้ `frontend-admin/.env.production` → `VITE_API_BASE_URL=https://api-admin.partner.syncvision.io`
5. deploy แล้ว**ทดสอบล็อกอินสองแอปพร้อมกันในเบราว์เซอร์เดียว** — นี่คือ acceptance test ของงานนี้

**ถ้าทำข้อ 4 ก่อนข้อ 1 แอดมินจะล็อกอินไม่ได้ทันทีที่ deploy**

### 3.2 V8 / V17 — ค่าใน `.env` ของ production

ยังรอผลคำสั่งเฟส 0 อยู่ ผมเข้าเซิร์ฟเวอร์ไม่ได้

```bash
grep -E "^(APP_ENV|APP_DEBUG|SESSION_SECURE_COOKIE|LOG_LEVEL|LOG_STACK)=" .env
```

ต้องเป็น `APP_DEBUG=false` · `SESSION_SECURE_COOKIE=true` · `LOG_LEVEL=warning` · `LOG_STACK=daily`

**และเพิ่มใหม่จากรอบนี้:** `FRONTEND_URL` กับ `ADMIN_FRONTEND_URL` **จำเป็นแล้ว** — เดิม `config/cors.php` ถอยไปใช้ค่า localhost เมื่อไม่ได้ตั้ง ตอนนี้ไม่ถอยแล้ว ถ้าไม่ตั้งค่าบน production จะไม่มี origin ไหนเรียก API ได้เลย (พังดัง ไม่พังเงียบ)

### 3.3 CSP ฉบับเต็ม — เขียนไว้ให้แล้วแต่ยัง comment ทิ้งไว้

`.htaccess` ทั้งสองแอปมี `frame-ancestors` (กัน clickjacking ซึ่งคือช่องโหว่ที่เจอจริง) เปิดใช้แล้ว
แต่ CSP ที่คุม `script-src`/`connect-src` **ยังปิดอยู่** พร้อมบรรทัดที่เตรียมไว้ในไฟล์

เหตุผล: CSP ที่ผิด**ไม่เตือน มันทำให้หน้าจอขาว** และทางเดียวที่จะจูนอย่างซื่อสัตย์คือเปิดทุกหน้าในเบราว์เซอร์จริงแล้วอ่าน console
ผมทำแบบนั้นไม่ได้จากที่นี่ การเปิดมันไปเลยคือแลกความเสี่ยง clickjacking กับความเสี่ยงเว็บล่ม

### 3.4 `sandbox` บน iframe — ยังไม่ใส่ และบอกเหตุผลตรง ๆ

ช่องโหว่จริง (V11) ปิดด้วยการกรอง protocol แล้ว ส่วน `sandbox` เป็นเกราะชั้นสอง
แต่ `sandbox` ที่ตั้งผิด**ทำให้คลิปหยุดเล่นแบบเงียบ ๆ ทั้งระบบ** และผมยืนยันในเบราว์เซอร์จริงไม่ได้ จึงไม่ใส่มั่ว ๆ

### 3.5 หน้าจอสำหรับปุ่มคืนเงิน — ยังไม่มี

API พร้อมและมีเทสต์ครบ แต่**ยังไม่มีปุ่มในหน้าแอดมิน** ต้องเรียก `POST /orders/{id}/refund` ด้วย `reason` เอง
เป็นงานฝั่งหน้าจอล้วน ๆ ที่แยกออกมาได้ บอกได้ถ้าจะให้ทำต่อ

### 3.6 เคสจ่ายเงินสด ยังตันเหมือนเดิม

จากเฟส 1 — ทางเดียวที่จะได้สถานะ `AwaitingVerification` คือลูกค้าอัปโหลดสลิปเองที่หน้า `/pay`
**ยังไม่ได้ทำฟีเจอร์ให้แอดมินอัปโหลดแทน** เพราะยังไม่มีคำตอบว่าใครควรทำได้
