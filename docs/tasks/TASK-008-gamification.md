Acceptance Criteria:

  - Repeating an already-completed module, or retaking-and-repassing an already-passed exam, never awards XP a second time — this is the farming-prevention guarantee (verified: `test_completing_a_module_awards_xp_once`'s second call, `test_retaking_and_repassing_an_already_passed_exam_does_not_award_xp_again`)
  - Submitting a referral or advancing a pipeline stage credits XP to the resolved agent, never to a Company Admin acting on their behalf (verified: `test_submitting_a_referral_awards_xp_to_the_referring_agent_not_the_admin_actor`, `test_pipeline_advance_credited_to_the_referrals_agent_even_when_a_different_actor_advances_it`)
  - Reaching Complete Payment awards both the generic per-stage XP and the payment-completion bonus (verified: `test_advancing_the_pipeline_awards_stage_xp_and_a_payment_bonus_to_the_agent`)
  - A missing `gamification_rules` config never blocks the triggering action (module completion, pipeline advance, etc.) — it logs a warning and awards nothing (verified: `test_no_xp_awarded_and_no_error_when_no_gamification_rule_is_configured`)

**Post-hoc bug fix (found while the human ran `php artisan test --filter=Gamification`):** `XpLedger` had no `protected $table` override, so Eloquent's default pluralization looked for `xp_ledgers` while the migration created the singular `xp_ledger` — every `awardXp()` call would fail with "no such table" against a real database. Same root-cause bug, independently present in `CommissionLedger` (see TASK-007's own post-hoc note) — both fixed the same way (`protected $table = '...'`). Neither the structural review nor `eslint`/`vue-tsc`/`vite build` could have caught this — it's a runtime-only SQL error, invisible to a static read-through or a frontend build. Re-run `php artisan test --filter=Gamification` (and `--filter=Commission`, since it shares the bug) to confirm both are now clean.

Design notes (not in CLAUDE.md, decided here — flag if wrong):
  - "Generic per-stage XP + a separate Complete Payment bonus" for pipeline advances is a reading of `GamificationSourceType`'s own two-case shape (`pipeline_stage_advanced` + `payment_complete` as distinct cases), not a guessed number — but CLAUDE.md never explicitly confirms both apply together.   - `GamificationRule`/`Badge` are deliberately NOT `TenantScope`'d (unlike almost every other business table in this codebase) so their nullable `company_id` platform-default rows stay visible to tenant-scoped users — this means their cross-company-access rejection mechanism is the Policy (403), not the global scope (404), which is a deliberate exception to the otherwise-uniform 404-via-TenantScope pattern used everywhere else.
