## 0. สรุปสำหรับผู้บริหาร

ผมอ่านโค้ดจริงทั้งระบบ แล้ว**เขียนเทสต์โจมตีและรันจริง**เพื่อพิสูจน์ ไม่ใช่แค่เดาจากรูปแบบโค้ด

**พิสูจน์ได้ด้วยเทสต์ที่รันผ่านแล้ว 3 ช่องโหว่** — ทั้งสามอันเป็นของจริง ไม่ใช่ทฤษฎี:

```
PASS Tests\Feature\Security\SecurityAuditProofTest
 ✓ ตัวแทนยืนยันการชำระเงินของออเดอร์ตัวเองโดยไม่มีสลิป แล้วได้คอมมิชชั่น
 ✓ แอดมินบริษัท A อ่านข่าวสารที่ยังไม่เผยแพร่ของบริษัท B ได้
 ✓ ตัวแทนบริษัท A อ่าน Badge / ของรางวัลส่วนตัวของบริษัท B ได้
 Tests: 3 passed (9 assertions)
```

**ข่าวดีที่ต้องพูดก่อน:** พื้นฐานความปลอดภัยของระบบนี้**แน่นกว่าค่าเฉลี่ยมาก** เงินเก็บเป็น integer สตางค์ทั้งระบบ
ไม่มี float สักคอลัมน์ · ราคาคำนวณฝั่งเซิร์ฟเวอร์ล้วน ไม่เคยเชื่อราคาจาก client · ไม่มี SQL injection สักจุด ·
ไม่มี `v-html` สักที่ในทั้งสองแอป · ไฟล์ลับอยู่ดิสก์ private และผ่าน authorize ทุกครั้ง · audit log แก้ไม่ได้จริง ·
งาน cron ที่จ่ายเงินมี `lockForUpdate()` ถูกต้อง

**ปัญหาที่เจอกระจุกอยู่ 3 กลุ่ม** ไม่ใช่กระจายทั้งระบบ:
1. **การแบ่งหน้าที่ (segregation of duties)** — คนที่ได้เงินเป็นคนกดยืนยันเงินเอง
2. **Policy ที่ `return true` แบบไม่ได้เช็คบริษัท** — 3 ตัวจาก 47 ตัว
3. **ค่า config บน production ที่ไม่มีใครยืนยัน** — ผมเข้าไปดูไม่ได้

## 2. รายละเอียดสามข้อที่พิสูจน์แล้ว

### 🔴 V1 — ตัวแทนปั๊มคอมมิชชั่นให้ตัวเองได้

**นี่คือข้อที่สำคัญที่สุดในเอกสารทั้งฉบับ**

`OrderPolicy::confirm()` อนุญาต `$order->agent_id === $user->id` — คือ**ตัวแทนเจ้าของออเดอร์เอง**
และ `OrderService::confirmPayment()` เช็คแค่ `isPayable()` ซึ่งแปลว่า "สถานะเป็น Pending หรือ AwaitingVerification"
**ไม่เคยเช็คว่ามีสลิปหรือยัง** ทั้งที่ `PaymentMethod` เขียนคอมเมนต์ตัวเองไว้ว่าทั้งสองวิธี "slip-verified"

**เส้นทางโจมตี** (ตัวแทนคนเดียวทำได้ครบ ไม่ต้องมีใครช่วย):
สร้างลูกค้าปลอม → สร้าง referral → เดินไปจนถึงขั้นก่อนชำระเงิน (ตัวแทนเดินเองได้) →
`POST /orders` → `POST /orders/{id}/confirm` → **ได้แถวคอมมิชชั่นจริงในบัญชีที่ BR-4 บอกว่าห้ามลบ**

**สิ่งที่ยังกั้นอยู่ (สำคัญ ต้องพูดให้ครบ):** เงินไม่ได้ออกจากบริษัททันที — ต้องมีแอดมินกด `markPaid` อีกชั้น
ดังนั้นความเสียหายจริงคือ**บัญชีคอมมิชชั่นถูกปนเปื้อนด้วยรายการปลอมที่ลบไม่ได้** และถ้าแอดมินจ่ายตามรายงานโดยไม่ตรวจทีละรายการ เงินก็ออกจริง

**ทางแก้ที่เสนอ 2 ชั้น:**
1. `confirmPayment()` ต้องบังคับ `status === AwaitingVerification` (แปลว่ามีสลิปแล้วจริง) ไม่ใช่แค่ `isPayable()`
2. **ถอดตัวแทนออกจาก `OrderPolicy::confirm()`** เหลือแค่แอดมินบริษัท / Super Admin

> ⚠️ **ข้อ 2 เป็นการตัดสินใจทางธุรกิจ ไม่ใช่ทางเทคนิค** — ถ้าตัวแทนของคุณยืนยันเงินเองอยู่ทุกวันตามกระบวนการจริง
> การถอดออกจะเปลี่ยนวิธีทำงานของทั้งบริษัท **ผมไม่ตัดสินใจแทน (BR-7)** ต้องให้คุณเลือก — ดู §5

### 🟠 V4 — แอดมินบริษัทอ่านข่าวสารข้ามบริษัทได้

`AnnouncementPolicy::view()` คืน `true` เสมอ และ `AnnouncementController::show()` กรองเฉพาะ `if ($user?->isAgent())`
มี 3 บทบาทในระบบ — Agent, CompanyAdmin, SuperAdmin — **CompanyAdmin หลุดออกจากตะแกรงทั้งสองชั้น**

โค้ดตรงนั้นมีคอมเมนต์ยาวอธิบายว่า TASK-156 ปิดรูนี้ให้ Agent แล้ว — **แต่เคสแอดมินไม่เคยถูกครอบ**
เห็นได้ทั้งฉบับร่าง ข่าวที่ตั้งเวลาไว้ และข่าวที่เจาะจง cert tier ของคู่แข่ง

### 🟠 V5 — ใครก็ได้อ่าน Badge / ของรางวัลข้ามบริษัท

`BadgePolicy::view()` และ `RewardItemPolicy::view()` คืน `true` เสมอ และ controller ทั้งสองตัวไม่กรองใน `show()`
ทั้งที่ `index()` ที่อยู่ห่างกันไม่ถึง 10 บรรทัดกรองถูกต้อง

หลุดคือ `condition_config` (ตรรกะการให้ Badge อัตโนมัติ) และ `cost_points` / `stock_quantity` ของรางวัล
= โครงสร้างแรงจูงใจภายในของคู่แข่ง

**เทียบให้เห็นชัด:** `GamificationRulePolicy::view()` ซึ่งเป็นพี่น้องกัน**เช็ค company_id ถูกต้อง**

## 4. สิ่งที่ทำถูกอยู่แล้ว — อย่าไปแก้

ส่วนนี้สำคัญพอ ๆ กับรายการช่องโหว่ เพราะมันบอกว่าควรแก้แค่ไหนถึงพอ

- **เงินเป็น integer สตางค์ทั้งระบบ** ไม่มีคอลัมน์ float/double สักตัว ไม่มี cast เป็น float สักตัว
- **ราคาคำนวณฝั่งเซิร์ฟเวอร์ล้วน** — `StoreOrderRequest` รับแค่ `referral_id` กับ `payment_method` ไม่มี endpoint ไหนรับ `price`/`total`/`amount` จาก client
- **ไม่มี SQL injection** — ไม่มี `whereRaw` เลยทั้งโปรเจกต์ ไม่มี controller ไหนรับชื่อคอลัมน์สำหรับ sort จาก query string
- **ไม่มี `v-html` สักที่** ในทั้งสองแอป ข้อมูลผู้ใช้ทุกตัวผ่าน `{{ }}` ที่ escape ให้อัตโนมัติ
- **TenantScope เขียนถูก** และทุกจุดที่ `withoutGlobalScopes()` (196 จุด) มีการเช็ค company_id ชดเชยเสมอ
- **ไฟล์ลับอยู่ดิสก์ private** สลิป/เอกสารลูกค้า/สื่อการขาย ผ่าน `authorize()` ก่อนสตรีมทุกครั้ง ไม่มี URL เดาได้
- **ชื่อไฟล์อัปโหลดสร้างใหม่เสมอ** จาก mime ที่ sniff จริง ไม่เคยใช้ชื่อจาก client → ปิด path traversal และ `shell.php.jpg`
- **audit log แก้ไม่ได้จริง** ไม่มี `updated_at` ไม่มี route update/delete ไม่มีโค้ดไหนเรียก
- **cron ที่จ่ายเงินกันการรันซ้ำถูกต้อง** ด้วย `lockForUpdate()` ใน transaction
- **`?company_id=` เชื่อเฉพาะ Super Admin** ผ่าน `CompanyScopeFilter` จุดเดียว ไม่มี header ปลอมได้
- **login ไม่บอกว่าอีเมลมีอยู่จริงไหม** ตอบเหมือนกันทุกกรณี และมี throttle
- **public endpoint ทุกตัวมี rate limit** และ token สุ่มด้วย `random_int` ไม่ใช่ `rand()`
- **ไม่มี `eval` / `exec` / `unserialize`** และการเรียก ffmpeg/pdftoppm ส่ง argument เป็น array ไม่ใช่ string
- **ไม่มี secret หลุดใน repo** และไม่มี `VITE_` ตัวไหนที่ไม่ควรเป็นสาธารณะ

## 5. คำตัดสินใจ — ล็อกแล้วโดย human 2026-08-21

| # | คำถาม | **คำตัดสิน** | ผลต่อการแก้โค้ด |
|---|---|---|---|
| D1 | ใครยืนยันการชำระเงินได้ | **Super Admin + แอดมินบริษัท · ตัดตัวแทนออก** | `OrderPolicy::confirm()` ต้องแยกออกจาก `ownsOrManages()` ที่ `view`/`cancel` ใช้ร่วมกันอยู่ ไม่ใช่แก้เมธอดกลางตัวเดียว มิฉะนั้นตัวแทนจะมองไม่เห็นออเดอร์ตัวเองไปด้วย |
| D2 | ต้องมีสลิปก่อนยืนยันไหม | **ต้องมี** สลิปก่อน แล้ว Super Admin ตรวจ | `confirmPayment()` บังคับ `status === AwaitingVerification` (= มีสลิปในระบบแล้ว) แทนที่จะเช็คแค่ `isPayable()` |
| D3 | ต้องมีการคืนเงินไหม | **ต้องมี · Super Admin เท่านั้น** | ฟีเจอร์ใหม่ ต้องเขียนสเปคแยก — เขียนแถวคอมมิชชั่น**ติดลบ**อ้างอิงแถวเดิม ไม่แก้ไม่ลบของเดิม (BR-4) |
| D4 | ยังต้องใช้ SVG ไหม | **ไม่จำเป็น** | ตัด `svg` ออกจาก `mimes:` ของ `CompanyThemeController` ให้ตรงกับ `StoreBrandRequest` |
| D5 | แยก session ยังไง | **เพิ่ม API subdomain ให้ฝั่งแอดมิน** | `api-admin.partner.syncvision.io` (ใหม่) สำหรับ admin · `api.partner.syncvision.io` (เดิม) สำหรับ agent |

### สิ่งที่ต้องรู้ก่อนลงมือ — ผลข้างเคียงของคำตัดสิน

**D2 มีเคสที่จะติด:** เส้นทางเดียวที่ทำให้ออเดอร์เป็น `AwaitingVerification` คือ**ลูกค้าอัปโหลดสลิปเองที่หน้า `/pay/<token>`**
ถ้ามีลูกค้าจ่ายเงินสดที่สาขา หรือโอนแล้วส่งสลิปมาทาง LINE ให้ตัวแทน — **หลังแก้แล้วจะยืนยันไม่ได้เลย เพราะไม่มีสลิปในระบบ**
ทางแก้ที่เสนอคู่กัน: เพิ่มให้**แอดมินอัปโหลดสลิปแทนลูกค้าได้**จากหน้าออเดอร์ เพื่อไม่ให้เคสนี้ตัน — ขอคำยืนยันว่าจะทำด้วยไหม

**D1 ไม่กระทบการยกเลิกออเดอร์:** ผมจะคงสิทธิ์ `cancel` ของตัวแทนไว้ตามเดิม เพราะการยกเลิกไม่สร้างคอมมิชชั่น
ถ้าอยากตัดออกด้วยบอกได้ แต่ผมไม่ทำโดยไม่ถาม

**D5 เป็นงาน DNS ก่อนงานโค้ด:** ต้องสร้าง subdomain `api-admin` ชี้ไปโฟลเดอร์ backend เดิม (แอปเดียวกัน คนละโฮสต์)
แล้วค่อยแก้ `.env.production` ของแอดมินไฟล์เดียว ถ้ายังไม่ได้สร้าง subdomain การแก้ `.env` จะทำให้แอดมินล็อกอินไม่ได้ทันที

## 7. สิ่งที่ผมตรวจไม่ได้ — บอกไว้ตรง ๆ แทนที่จะเดา

1. **ค่า `.env` จริงบน production** — ไฟล์ถูก gitignore และผมเข้าเซิร์ฟเวอร์ไม่ได้ (เฟส 0 คือข้อนี้)
2. **`composer audit`** — sandbox นี้ถูกบล็อกไม่ให้ต่อ `repo.packagist.org` (403) **ต้องรันบนเครื่องคุณ**
   ผมตรวจเวอร์ชันด้วยมือแล้ว: Laravel 12.66, Symfony 7.4, Sanctum 4.3.3 ไม่มีตัวไหนค้างเมเจอร์เก่า แต่**นั่นไม่ใช่การเช็ค CVE จริง**
3. **`.env` เข้าถึงผ่านเว็บได้ไหม** — ขึ้นกับว่า Hostinger ชี้ document root ไปที่ `public/` หรือชี้สูงกว่านั้น ทดสอบได้ด้วยการเปิด `https://api.partner.syncvision.io/.env` ตรง ๆ (ควรได้ 403/404)
4. **การสำรองข้อมูลและการหมุน APP_KEY** — ไม่มีเอกสารในโปรเจกต์
5. **V2 (คอมมิชชั่นซ้ำ) ผมยืนยันจากการอ่านโค้ด ไม่ได้พิสูจน์ด้วยเทสต์** — การพิสูจน์ race condition ต้องยิงพร้อมกันจริง ซึ่งเทสต์ SQLite in-memory ทำไม่ได้
