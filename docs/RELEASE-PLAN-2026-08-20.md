## 2. ⚠️ ความเสี่ยงอันดับ 1 ของรอบนี้ — อ่านก่อนอย่างอื่น

**TASK-214 เปลี่ยนวิธีคิดค่าคอมหัวหน้าทีม และ deploy จะรัน `migrate --force` ให้อัตโนมัติ**

หลัง migrate ทันที ระบบจะ**เลิกอ่าน cert tier** ในการเลือกอัตราหัวหน้าทีม
ถ้า production มีอัตราหัวหน้าทีม **มากกว่า 1 ใบต่อบริษัท** (เช่นเคยตั้งแยก
Basic / Intermediate / High) ทั้งหมดจะตกไปอยู่ scope เดียวกันทันที และ
**ดีลที่ปิดในช่วงนั้นจะจ่ายหัวหน้าทีมด้วยอัตราที่ทำนายไม่ได้** — ลง ledger แล้วแก้ไม่ได้ (BR-4)

### เช็ค 30 วินาทีที่ทำได้เดี๋ยวนี้ ก่อนตัดสินใจอะไรทั้งนั้น

เปิด **production → แผนคอมมิชชั่น → ค่าคอมหัวหน้าทีม (Override)** แล้วนับ

- **มีใบเดียวต่อบริษัท** → ไม่มีความเสี่ยงเลย deploy ได้สบาย
- **มีหลายใบแยกตาม tier** → ต้องทำตามข้อ 5.1 ทันทีหลัง deploy
  และควรเลือกเวลา deploy ตอนที่ไม่มีคนปิดการขาย

## 3. ลำดับที่แนะนำ

### 3.1 แตก commit ก่อน — อย่ายัด 177 ไฟล์เป็นก้อนเดียว

commit เดียวแปลว่า **ถ้าอะไรพังจะ revert ทีละเรื่องไม่ได้** ต้องถอยทั้งรอบ
ผมเสนอ 10 commit ตามงาน:

| # | ขอบเขต |
|---|---|
| 1 | ADR-036 แคตตาล็อกกลาง + แบรนด์/หมวดหมู่ข้ามบริษัท (TASK-202..205) |
| 2 | TASK-206 ซ่อม taxonomy ของสินค้าที่ผูกแคตตาล็อก + คำสั่ง backfill |
| 3 | ADR-038 ขอบเขตบริษัทของ Super Admin (TASK-208/209) |
| 4 | TASK-210 โมดัลแจ้งบันทึกสำเร็จ |
| 5 | TASK-211 สาขาไม่บังคับ + ฟอร์มบอกช่องที่ขาด |
| 6 | TASK-212 ส่งลิงก์ทางอีเมลผ่าน SMTP ของระบบ |
| 7 | TASK-213 รวมศูนย์หน้าค่าคอม + ตัวตรวจอัตราซ้อนทับ |
| 8 | **TASK-214 อัตราหัวหน้าทีมแยกรายสินค้า (มี migration + เปลี่ยนการคำนวณเงิน)** |
| 9 | TASK-215 Commission Ledger แยกประเภทเงิน + คำสั่ง audit |
| 10 | TASK-216 ฟอร์มเป็น modal + หัวข้อบอกว่าแก้ตัวไหน |

**commit ที่ 8 คืออันเดียวที่แตะเงิน** — แยกไว้เพื่อให้ revert ได้เดี่ยว ๆ ถ้าจำเป็น

### 3.2 ขึ้น GitHub

ผมแนะนำ **branch → PR → merge** ไม่ใช่ push main ตรง ๆ

```bash
git checkout -b release/2026-08-20-commission
# ...commit ตาม §3.1...
git push -u origin release/2026-08-20-commission
# เปิด PR บน GitHub → merge เข้า main
git checkout main && git pull
```

เหตุผล: งานรอบนี้ใหญ่ผิดปกติ (177 ไฟล์) การมี PR หนึ่งใบทำให้ย้อนกลับมาอ่าน
ได้ว่ารอบนี้เปลี่ยนอะไรบ้าง โดยไม่ต้องไล่ commit ทีละใบ — **และไม่กระทบวิธี deploy เดิม**
เพราะสุดท้ายก็ deploy จาก `main` เหมือนเดิม

> ถ้าไม่อยากมีขั้นตอน PR: commit ลง `main` ตรง ๆ ก็ใช้ได้ ไม่ผิด — แค่เสียประวัติที่อ่านง่ายไป

### 3.3 Deploy

```bash
npm run deploy
```

## 4. ก่อนกด deploy — ตรวจ 4 อย่าง (ผมตรวจให้ไม่ได้)

| # | ต้องรัน | ทำไม |
|---|---|---|
| 1 | `cd frontend-admin && npm run build`<br>`cd frontend && npm run build` | **deploy จะพังตรงนี้ถ้า build ไม่ผ่าน** · ผมรันจากที่นี่ไม่ได้ (node_modules เป็น macOS build) — ผ่านแค่ `vue-tsc` ซึ่งเป็นครึ่งเดียวของ build |
| 2 | `cd backend && php artisan test` | ผมรันบน sqlite ในคลาวด์ได้ **1631 passed** แต่ยังไม่เคยรันบน **MySQL ของคุณ** |
| 3 | `npm run test:unit` ทั้งสอง frontend | ผมรันไม่ได้เลยทั้งเซสชัน (rolldown native binding) |
| 4 | **บนเซิร์ฟเวอร์:** `php artisan migrate:status \| tail -20` | ดูว่ายังมี migration ค้างจากรอบก่อนไหม โดยเฉพาะ `2026_08_24_090200_move_lesson_quiz_questions_onto_quizzes` — ตัวนี้ **ล้มบน MariaDB (errno 121)** ตอนผมทดสอบ ถ้ามันยังไม่ถูกรันบน production มันจะพัง deploy ครั้งนี้ |

**ข้อ 4 สำคัญกว่าที่คิด** — `deploy.sh` ใช้ `set -e` และสั่ง `php artisan down` ก่อน
ถ้า migrate ล้ม สคริปต์จะหยุดกลางทางและ **เว็บค้างอยู่ในโหมด maintenance**
(สคริปต์เตือนไว้เองว่าให้ SSH เข้าไปสั่ง `php artisan up`)

## 5. หลัง deploy — ทำทันที ตามลำดับ

### 5.1 รวมอัตราหัวหน้าทีมที่ชนกัน (ถ้ามี)

```bash
php artisan commission:collapse-override-tiers --dry-run   # ดูก่อน
php artisan commission:collapse-override-tiers             # ตอบคำถามถ้ามีอัตราต่างกัน
```

**ยิ่งเร็วยิ่งดี** — ช่วงระหว่าง migrate เสร็จกับคำสั่งนี้ คือช่วงที่ค่าคอม
หัวหน้าทีมทำนายไม่ได้

### 5.2 หาการขายที่ปิดแล้วแต่ตัวแทนไม่เคยได้ค่าคอม

```bash
php artisan commission:audit-unpaid-closures
```

บน local เจอ **3 รายการ** (ปิดตั้งแต่ 13 ส.ค. ได้แค่โบนัสแคมเปญ ไม่มีค่าคอม)
production อาจมีเหมือนกัน · อ่านอย่างเดียว ไม่แก้อะไรให้

### 5.3 เช็คหน้าจอ 3 จุด

- **แผนคอมมิชชั่น → ภาพรวมสินค้า** → ต้องไม่มีสินค้าไหนขึ้นแดง
- **Commission Ledger** → แถวต้องมีป้ายประเภท (ค่าคอมของตัวเอง / หัวหน้าทีม / โบนัสแคมเปญ)
- **ตั้งค่า Email SMTP** → ถ้ายังไม่ได้ตั้งบน production ปุ่ม "อีเมล" ในโมดัลแชร์
  จะขึ้น 422 (TASK-212) — ตั้งค่าแล้วกด "ทดสอบส่งอีเมล" ให้ผ่านก่อน

## 6. ถ้าต้องถอย

**โค้ดถอยได้ ข้อมูลถอยไม่ได้** — พูดให้ชัดตั้งแต่ตอนนี้ดีกว่าไปรู้ตอนนั้น

| ถอยได้ | ถอยไม่ได้ |
|---|---|
| โค้ด — deploy commit เก่าทับ | แถว `commission_ledger` ที่เขียนไปแล้ว (BR-4) |
| | แถวที่ `collapse-override-tiers` ลบไปแล้ว |
| | `down()` ของ migration TASK-214 **จะล้ม** ถ้ามีแถวใหม่ที่ `manager_cert_tier_id` เป็น NULL — เขียนไว้แบบนั้นตั้งใจ ไม่ให้เดาค่า tier ขึ้นมาใหม่ |

→ **สำรอง DB ก่อน deploy** (hPanel → Backups หรือ `mysqldump`) นี่คือทางถอยเดียวที่ครอบคลุมข้อมูล

## 7. สิ่งที่ยังไม่ผ่านการทดสอบ — ขึ้นทั้งที่รู้ว่ายังไม่ได้ทดสอบ

| เรื่อง | สถานะ |
|---|---|
| หน้าแผนคอมมิชชั่น + Ledger + modal | ✅ กดจริงในเบราว์เซอร์แล้ว |
| การคำนวณค่าคอม (ตัวแทน + หัวหน้าทีม) | ✅ ปิดการขายจริง ตัวเลขตรง |
| **แอปตัวแทน (frontend)** — TASK-210/211/212 | ❌ **ยังไม่ได้กดจริงเลย** |
| ส่งอีเมลผ่าน SMTP จริง (TASK-212) | ❌ ยังไม่เคยส่งจริงสักครั้ง |
| UAT-016 ครบสคริปต์ (3 ลูกทีม + เคสปัดเศษ) | ❌ ทำแค่บางส่วน |
| vitest ทั้งสอง frontend | ❌ รันไม่ได้ทั้งเซสชัน |

**ข้อเสนอ:** ถ้าอยากลดความเสี่ยง ให้กดทดสอบ **แอปตัวแทน** สัก 10 นาที
ก่อน deploy — เพิ่มสินค้าที่สนใจ 1 ครั้ง, กดแชร์ลิงก์ 1 ครั้ง, แก้ข้อมูลตัวแทน 1 ครั้ง
สามอันนี้คือของที่แก้ไปแล้วยังไม่มีใครกดเลย
